> Estado: **🔮 planeado — bloqueado por acceso al spec.** Nada de esto está
> construido. Este doc fija el diseño del *seam* de proveedor y deja por escrito
> qué falta para poder escribir la primera línea del adaptador.
> Leer junto con `docs/01-SALES-ENGINE.md` §3.3 (cobro en línea),

## 1. Qué se pidió, y por qué importa más de lo que parece

Que **360pay sea la opción de cobro por defecto** del checkout, en lugar de que
el cobro en línea sea sinónimo de Culqi.

Esto no es un cambio de proveedor por gusto. Hoy **el cobro en línea no funciona
en producción**: `culqi_enabled = false` en Gadicaf desde el 12-ago-2026 porque
la API directa de Culqi responde `400 authentication_error` mientras no se
acredite PCI DSS y se apruebe el SAQ-D — es el **bloqueo #1** de
`ESTADO-OPERATIVO.md`, y su dueño es el fundador, no el código.

O sea: 360pay es candidato a **destrabar el bloqueo #1**, no solo a acompañar a
Culqi. Eso sube el valor de hacerlo y agrega una pregunta que no existía —
§6.0 — que hay que responder **antes** que ninguna otra: si 360pay exige el
mismo papeleo PCI, cambiar de motor no destraba nada y el esfuerzo va a otro
lado.

Mientras tanto el checkout **sí vende**: el paso 3 va por el flujo manual
(Yape de la marca + código de seguridad de 3 dígitos + cruce por `yape-ingest`),
que está probado y en producción.

## 2. Por qué no se implementó todavía

El contrato del API no se pudo leer. `api.360pay.pe`, `sandbox.api.360pay.pe` y
`360pay.pe` están **bloqueados por la política de egress** del entorno remoto
(el gateway responde `403` al CONNECT). No es un fallo transitorio ni un
problema de TLS: es denegación de política.

Escribir el cliente HTTP adivinando nombres de campo es exactamente el error que
no se puede cometer en el módulo que mueve dinero: un campo mal nombrado no
falla ruidosamente, cobra mal o no cobra. Así que el adaptador queda sin
escribir hasta tener el spec. Ver §6.

el reducer, en la config de tienda y en el panel. Inventario real:

## 4. La decisión de diseño: `payment_provider` sube a `stores`

Hoy `payment_provider` solo existe en el pedido, y se escribe desde el front.
El seam correcto es que la tienda declare su motor y el pedido herede:

```
stores.payment_provider  text  DEFAULT '360PAY'   -- '360PAY' | 'CULQI' | NULL(manual)
```

Con eso, "360pay por defecto" es literalmente el `DEFAULT` de esa columna, y
Culqi pasa de ser *el* cobro en línea a ser *un* motor más. `culqi_enabled` /
`culqi_scope` se generalizan a `online_pay_enabled` / `online_pay_scope`
(mismos valores, misma semántica de repliegue operativo).

En el front, `StoreCulqi` → `StoreOnlinePay { provider, enabled, scope }` y
`culqiActiveFor()` → `onlinePayActiveFor()`. La forma del estado no cambia; solo
deja de asumir el motor.

**Invariantes que se mantienen tal cual** — son del dominio, no de Culqi:
el monto se re-deriva SIEMPRE en el servidor y se contrasta contra la fila; las
credenciales se resuelven por `origin_store_id`, jamás por la tienda del
vendedor asignado; un claim-lock por pedido; `network_after` nunca reintenta.

## 5. Modelo de credenciales: ojo, **no** es el de Culqi

La llave entregada es de **partner** (`pt_…`) y el doc apunta a
`#tag/businesses`. Eso describe un modelo distinto al de Culqi: Kross sería el
partner y **cada marca un "business" creado bajo la cuenta de Kross**, en vez de
que cada marca pegue sus propias llaves.

Si se confirma, el almacenamiento cambia de raíz:

- **una** llave de partner a nivel plataforma → secret de Supabase
  (`supabase secrets set`), NUNCA en `store_secrets` ni en el repo;
- `stores.pay360_business_id` (identificador público, no secreto) por marca;
- `MarcaPage` deja de pedir llaves y pasa a mostrar el estado de onboarding del
  business.

Es una hipótesis derivada del nombre del tag y del prefijo de la llave. **Hay
que confirmarla contra el spec antes de migrar nada**, porque decide si
`store_secrets` participa o no.

## 6. El contrato real (OpenAPI leído el 18-ago-2026)

Public API v1.1.0 y Partner API v1.0.0, ambos OpenAPI 3.0.0.

| | Public API | Partner API |
|---|---|---|
| Producción | `https://api.360pay.pe/v1` | `https://api.360pay.pe/partners/v1` |
| **Sandbox** | `https://sandbox.api.360pay.pe/v1` | `https://sandbox.api.360pay.pe/partners/v1` |
| Auth | `x-api-key` (o Bearer) — key del **negocio** | `x-api-key` (o Bearer) — key del **partner** |

Sobres: éxito `{success, data, message}`; listas `{success, data[], meta{total,page,limit,total_pages}}`;
error `{success:false, error:"…", required_scopes?:[…]}` — el `403` **dice qué scope falta**.

### 6.a El modelo: cupón = orden de cobro bancaria

`POST /coupons` — obligatorios **`amount`** y **`external_ref`**; opcionales `customer_id`
(o un objeto `customer` para crear cliente y cupón en una sola llamada), `description`,
`issue_date`, `expiry_date`.

```
201 → { _id, business_id, customer_id, coupon_code:"EMP1001-0001",
        external_ref:"ORD-9988", amount:150.5, status:"active", … }
```

Dos cosas que fijan el adaptador:

- **`amount` va en SOLES con decimales** (`150.5`), no en céntimos. Es lo contrario a
  Culqi, que cobra en céntimos. Un adaptador que reutilice `Math.round(pen * 100)`
  cobraría **100 veces de más**.
- **`external_ref` es nuestra llave de idempotencia natural**: ahí va el id del pedido, y
  es por donde el webhook vuelve a encontrar la sesión.

Ciclo de vida observado: `active` → `paid` → (o `voided` vía `PUT /coupons/{id}/annul`,
que da `409` si no está activo).

Al pagarse, el cupón gana: `paid_at`, `payment_date`, **`bank_tx_id`** (`"BCP"`,
`"SCOTIABANK"`, `"INTERBANK"`, `"BBVA"`), `operation_number`, `fee_platform`,
`fee_partner`, y después `settlement_id` / `settlement_status`.
El Partner API agrega **`payment_reference`** (ej. `"A1B2C3D4E5F6G7"`) — el código con el
que el comprador paga.

### 6.b ⛔ El hallazgo que decide todo: **no existe endpoint que cobre**

Revisados los dos specs completos, **ninguno tiene una operación de cobro**. No hay
tokenización, no hay Yape, no hay tarjeta, no hay OTP, y el `201` de crear cupón **no
devuelve ninguna URL de pago ni link de checkout**.

Lo que sí hay dice qué es esto en realidad: los bancos de `bank_tx_id` son BCP,
Scotiabank, Interbank y BBVA; el negocio se crea con `source_account`,
`destination_account`, `destination_bank` y tramos de comisión; y existe `payment_reference`.

**360pay es un riel de RECAUDACIÓN bancaria, no una pasarela de checkout.** El flujo es:
emitimos el cupón → **el comprador lo paga en su banco** (app, agente o ventanilla)
citando la referencia → 360pay detecta el movimiento, marca `paid` y dispara
`PAYMENT_PAID` → el dinero se liquida al `destination_account` menos comisiones.

Esto **no puede reemplazar el cobro del checkout tal como está**. Hoy el paso 3 pide un
adelanto de S/5 (Lima) a S/30 (provincia) en una compra por impulso, y se cobra con Yape
en la misma pantalla. Mandar a ese comprador a abrir su app del banco, buscar "pagar
servicios" y tipear una referencia de 14 caracteres —por S/5— es más fricción que todo el
checkout junto.

### 6.c El intercambio real, para decidirlo con los ojos abiertos

No todo es costo. Contra el flujo manual de hoy, 360pay **gana en lo que hoy es frágil**:

| | Yape manual (hoy) | 360pay (cupones) |
|---|---|---|
| Fricción para el comprador | baja: yapea y copia 3 dígitos | **alta**: sale de la app, va a su banco |
| Confirmación | `yape-ingest`, que depende de un APK/MacroDroid vivo en un Android ajeno | **webhook firmado (HMAC)**, sin hardware nuestro |
| Certeza del cruce | heurística por monto + código | **determinística**: `external_ref` |
| PCI / SAQ-D | no aplica | **no aplica** — nunca tocamos credenciales de pago |
| Conciliación | manual | `settlements` con `fee_platform` / `fee_partner` |

O sea: **se cambia conversión por confiabilidad**, y de paso se esquiva el bloqueo #1
completo. Es una decisión de negocio, no de código.

### 6.d Onboarding y webhooks — esto sí está completo

`POST /partners/v1/businesses` crea el negocio y **sus hooks en la misma llamada**:

```
{ business: { name, email, payment_prefix:"EMP" },
  config:   { source_account, destination_account, destination_bank,
              commission_fixed_amount, commission_tiers[], partner_fee_override },
  hooks:    [ { type:"PAYMENT_PAID", url, headers?, payload_mapping?, active? } ] }
```

```
201 → data: { business_id, payment_prefix, config_id, hook_ids[],
              hook_signing_secrets:[{ hook_id, signing_secret:"whsec_…" }] }
```

**`hook_signing_secrets` se muestra UNA sola vez.** Si no se captura en esa respuesta, hay
que rotar con `POST /businesses/{businessId}/hooks/{hookId}/rotate-secret`. Va a
`store_secrets`, nunca a `stores`.

Confirma además el modelo de credenciales de §5: **una key de partner nuestra + un
`business_id` por marca**. No hay llaves por tienda que el comerciante pegue.

## 9. Preguntas enviadas a 360pay (18-ago-2026)

Ordenadas por lo que bloquean. Las 1–3 deciden **si** 360pay entra al checkout;
las 4–6 son para escribir el adaptador; la 7 puede matar el caso de uso por
economía aunque todo lo demás salga bien.

1. **¿Cómo paga el comprador un cupón?** ¿Solo por banca (app, agente,
   ventanilla) citando `payment_reference`, o existe **Yape/Plin**, o un **link
   de pago** que el OpenAPI no documenta?
2. **¿Hay algún cobro instantáneo?** Nuestro checkout cobra un adelanto de
   S/5–S/30 dentro del modal; hoy con Yape se confirma al toque. ¿Existe algo
   equivalente, o el modelo siempre es emitir cupón y esperar el webhook?
3. **¿Exige acreditación PCI DSS / SAQ-D de nuestro lado**, o el cumplimiento
   queda en ustedes por el modelo de partner? *(Es exactamente lo que tiene
   bloqueado el cobro con Culqi — ver `05-PCI-SAQ-D.md`.)*
4. **Firma del webhook:** algoritmo del HMAC, qué se firma exactamente (¿el body
   crudo?) y formato del header `X-360Pay-Signature`.
5. **Payload del evento `PAYMENT_PAID`**: campos que trae y **cuál es el
   identificador de evento** para idempotencia en reintentos.
6. **Scopes** de nuestra API key de partner: lista completa y cuáles pide cada
   operación (el `403` devuelve `required_scopes`, pero mejor saberlo antes).
7. **Economía en montos chicos.** `commission_fixed_amount` y `commission_tiers`
   sugieren comisión fija. **Sobre un adelanto de S/5, una comisión fija se come
   el cobro.** ¿Cuál es el mínimo por cupón y cuál sería nuestra tarifa?
8. **Tiempo típico** entre que el comprador paga en el banco y llega el
   `PAYMENT_PAID`: ¿segundos, minutos, o depende del banco?
9. **Sandbox.** El OpenAPI lista `sandbox.api.360pay.pe`, pero la llave entregada
   tiene prefijo `pt_live_`. ¿Es la correcta para sandbox?
10. **Moneda.** El spec nunca nombra PEN — confirmar que `amount` es siempre
    soles (y que va con decimales, no en céntimos).
